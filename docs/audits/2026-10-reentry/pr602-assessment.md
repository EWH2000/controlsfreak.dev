## What the build guards do to the owner's next English-only edit

Under the PR's guards, next week's English-only work makes the build FAIL. It never warns. Every guard collects its offenders and then throws. html/_data/i18nStatus.js sets completeLocales: ['ko'].
(1) New English-only tool, lesson or simulator page with a canonical: i18nPageGuard's 'ko canonical bijection — missing 1' throws. The section landing (tools/index.html etc.) also gains a card, so the ko landing's sourceContentHash and its structure signature both fail. If home-page counts change, ko/index.html fails too. tests/i18n.spec.js's sitemap bijection test fails as well.
(2) New quiz bank: i18nSourceDataGuard throws, because the ko.quizzes key set must equal the html/_data/quizzes files exactly. localizeQuiz throws 'Missing quiz translation overlay: ko/<slug>' when head.njk renders FAQPage JSON-LD. The ko practice page is also missing, which breaks the bijection. Editing or adding a single question in an existing bank changes that bank's SHA-256 (hash of the whole question array) and fails. The quiz-bank growth arc is exactly this kind of work.
(3) New glossary entry, or any edit to a term or def: the hash over glossary {term, def} fails. The glossary guard also requires the ko overlay keys to match English exactly, and the gloss transform throws 'missing ko glossary translation' for any mark that uses an untranslated id.
(4) Any edit to an existing English page's content block or translatable frontmatter (title, description, keywords, navLabel, pageMessages, faqs, termSets): the ko twin's sourceContentHash (and sourceMessageHash) no longer matches, so the build fails. A markup change (an added <p>, link, class, id, data-* attribute, data-gloss mark, or flag attribute) also fails compareSignature until the ko HTML gets the identical tag/attribute sequence. Edits only to {% block head %} styles, {% block scripts %} inline JS, shared scripts, styles.css, tests and docs do NOT trip it. A new user-visible string added the new way (a pageMessages key or i18n.js catalog key) needs a ko twin. One added the old way (hard-coded English in JS) passes silently and shows English on the Korean page.
(5) BACnet enum desc or new rows: the hash and the overlay key check fail.
So, to the brief's question: yes, effectively every future English content edit needs a Korean twin edit plus re-pinning SHA-256 values in frontmatter or i18nSourceHashes.js. The error message prints the exact expected hash, so an owner or agent who cannot read Korean can paste it and turn the 'reviewed' guarantee into a rubber stamp. The structure check still forces hand edits to Korean markup.
Escape hatch, read from the code: removing 'ko' from completeLocales turns off the bijection, 404, source-data-hash and BACnet-overlay checks. But i18nSourceDataGuard then fails until the ko block in i18nSourceHashes.js is also removed. More importantly, the per-page sourceContentHash and structure checks are NOT gated by completeLocales; they run on every translated page that exists. The only real off-switch is deleting the Korean twins.
Measured exposure: 82 of the 173 merges to main between 2026-07-28 and 2026-08-30 touched a guarded English surface (section/hub/home .html, _data/quizzes, glossary.js, bacnetEnums.js). That is an upper-bound proxy, since some touched only head/scripts blocks. Even so, it suggests roughly half of the owner's recent PRs would have gone red. CLAUDE.md's 'Adding a new tool / lesson / quiz' checklists are not updated to mention any of this, so the owner's agent lanes would discover it by build failure.

## Maintenance burden

For a solo maintainer who does not read Korean, the burden is high and permanent. (1) A Korean-twin obligation on roughly half of all merges, as above. The owner cannot write or verify the Korean, so each English edit means machine-translating, pasting the printed hash, or blocking. (2) The English authoring model changes on 61 pages: runtime copy now lives in YAML `pageMessages` frontmatter (with HTML entities such as &#39;), fetched through CFI18n.page(), which throws at runtime on a missing key. New strings on any page must follow this pattern, or the Korean page silently shows English. (3) The most actively developed surfaces are mirrored in full. ko/simulators/ddc-workbench.html (2,196 lines) and ddc-workbench-fcu.html (1,130 lines) duplicate the workbench content markup, so every workbench markup change must be repeated identically in Korean. That is the kind of stale-count claim the house rules warn about, and it will fail the build if pages are ever retired below 134. (5) House conventions are now doubled: privacy policy cf_* key list (two privacy pages), no-coming-soon copy (the Korean faithfully mirrors existing English violations, e.g. balancing.html's 'it'll get its own lesson when it's written', which now has to be fixed twice), the glossary curation rules (data-gloss marks placed in Korean prose the owner cannot read), and the owner's first-person anecdotes rendered in a language he cannot proof. (6) Test coverage gap: tests/pages.js is unchanged, so the blocking contrast-sweep and responsive (phone-overflow) specs never visit Korean pages. Only i18n.spec.js's smoke-style mirror test covers them. (7) Docs drift: CLAUDE.md only edits the description bullet. docs/i18n.md holds the real workflow, and the CLAUDE.md checklists, merge-approval section and README tour don't reference it.
