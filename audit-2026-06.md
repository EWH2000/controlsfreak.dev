# audit-2026-06.md

Master findings document for the **June 2026 extensive site audit** —
a multi-phase pass combining fresh-lens persona walkthroughs, a
codebase audit, content spot-checks, and mechanical sweeps. Successor
in spirit to `ux-audit.md` (2026-05-29, three personas) but wider in
scope and run *after* the PID process visual, IndexNow, status-pill
consolidation, and touch-target floor all shipped.

## How this file is used

- Findings are **report-only**. The audit is an extra set of eyes;
  editorial and design decisions stay with the site owner. Suggested
  directions are pointers, not finished rewrites.
- This is the **master doc**: everything lands here first. After the
  owner triages, confirmed items get cross-filed into
  `codebase-issues.md` / `content-audit.md` / `site-ideas-and-friction.md`
  per their conventions — nothing is cross-filed yet.
- **Severity**: **high** = blocks or actively misleads the persona;
  **medium** = real friction or trust damage, task still completes;
  **low** = polish. Where the verification pass argued a different
  severity than the finder, the note says so.
- Every finding was **adversarially verified**: a skeptic agent per
  persona/specialist re-reproduced each claim against the live build
  and checked it against `CLAUDE.md` Gotchas, `ux-audit.md`,
  `content-audit.md`, `codebase-issues.md`, and
  `site-ideas-and-friction.md`. Across both rounds, **113 findings
  were raised: 107 confirmed**, 5 redirected to existing entries,
  1 refuted. Skeptic corrections are folded into the finding text.
- Phase-1 evidence screenshots live under `/tmp/audit-2026-06/<persona>/`
  (throwaway — repro steps in each finding are the durable evidence).

# Phase 1 — persona walkthroughs (2026-06-09)

## Substantive findings (1–30)

### Units & metric

#### 1. Metric enthalpy uses the IP zero-datum — every displayed h is ~17.8 kJ/kg high, and typing a real SI enthalpy produces a wrong state plus a false error verdict — **high**

**Location:** `scripts/units.js:57` (and the toCanonical path) →
dew-point-calculator, coil-sizing, air-mixing, psychrometric-chart,
economizer-ratio. **Lens:** metric. **Verified:** reproduced both
directions; hand-check 1.006·23.89 + 0.01017·(2501 + 1.86·23.89) =
49.9 kJ/kg confirms the SI expectation.

`units.js` converts enthalpy with a pure scale (`h × 2.326`), but IP
enthalpy is zeroed at 0 °F dry air while SI is zeroed at 0 °C — a
constant offset of 0.240·32·2.326 = **17.86 kJ/kg**. Display side:
dew-point's metric default (23.9 °C / 55 % RH) shows **67.8 kJ/kg**
where every SI table/Mollier chart says **~50.0**. Input side: on
coil-sizing in metric, Define-by = Enthalpy, DB 23.9, h 50 (the
*correct* SI value) → the tool reads it as 21.5 Btu/lb, outputs
SHR −4.52 and the verdict "a cooling coil removes water, it can't add
it" — blaming valid SI inputs. Δh capacities are unaffected (offset
cancels), which is why the prior content audits (which spot-checked
the ×2.326 factor, never the datum) didn't catch it.

**Suggested direction:** make the metric enthalpy conversion
datum-aware in `units.js`: display `h_SI = (h_IP − 7.686) × 2.326`,
toCanonical `h_IP = h_SI / 2.326 + 7.686` (ASHRAE SI convention,
h = 0 for dry air at 0 °C).

#### 2. Units toggle is rendered but dead on ~34 pages that don't load `units.js` — clicks do nothing and the choice doesn't persist — **high** (verifier: arguably medium)

**Location:** `nav.njk` (pill on every page) vs the per-page
`units.js` loading convention — all 21 practice pages, 8 lessons,
3 simulators, 3 tools (full list via `grep -rL 'units.js' html/`).
**Lens:** metric. **Verified:** reproduced on
/education/superheat-subcooling.html — `window.Units` undefined,
clicking US leaves `data-units` and localStorage at `metric`.

A metric visitor whose first landing is a lesson or quiz clicks
Metric, sees zero response (the control reads as broken), and the
preference isn't saved for the rest of the site either. Sharpening
from verification: the *visual* pressed state is correct on these
pages (CSS keys off `html[data-units]` set by the head bootstrap),
but the hard-coded `aria-pressed="true"` on US never re-syncs at all
here — permanently wrong for metric screen-reader users, worse than
the documented flicker gotcha. Verifier argues medium since nothing
on these pages converts (harm is the broken-feeling control, not
wrong data); the finder's high reflects first-impression damage.

**Suggested direction:** load `units.js` site-wide from
`layouts/page.njk` exactly like `theme.js` — it's small and its DOM
walker no-ops without `data-us` spans.

#### 3. The refrigeration content cluster (3 lessons + quizzes) is imperial-only while its paired tool converts fully — **medium** *(cross-filed → content-audit.md #35, 2026-06-10)*

**Location:** education/superheat-subcooling (23 imperial hits,
0 `data-metric` spans), refrigerant-cycle-basics (15/0),
metering-devices-txv-eev (19/0); quiz banks superheat-subcooling
(numeric answer demanded "in °F"), sequencing-scenarios,
psychrometrics-basics, hydronic-loops. **Lens:** metric.
**Verified:** in source; `refrigerant-education-plan.md`'s units rule
is gauge-vs-absolute, not US-vs-metric — no doc decides imperial-only.

The superheat lesson tells the reader to cross-check in the
refrigerant-pt tool — which in metric shows the same system as
814 kPag / 4.3 °C, so the numbers don't connect. Fix depends on
finding 2 (these pages don't load `units.js`, so `data-metric` spans
would never swap today).

**Suggested direction:** dual-state the lesson worked examples with
the existing span convention (the tool already computes the metric
equivalents); for quizzes, at minimum dual-state prompts
("48 °F (8.9 °C)").

#### 4. Worked-example formula/plug-in steps keep IP-only constants and numbers in metric, contradicting the converted prose around them — **medium** *(cross-filed → content-audit.md #36, 2026-06-10)*

**Location:** coil-sizing (`ṁ = CFM × 60 ÷ v`,

**Verified:** all cited line numbers confirmed; distinct from

### Accessibility

#### 6. Open mobile nav sheet is unreachable by forward Tab; subsequent focus disappears off-screen behind the scroll lock — **high**

**Location:** `_includes/nav.njk` (DOM order: `#site-nav-links`
precedes `#nav-hamburger`) + `nav-menu.js` (no focus management on
sheet open; focusout-close covers only desktop dropdowns). Site-wide
chrome at ≤620px — including desktop browser zoom. **Lens:** a11y.
**Verified:** reproduced exactly at 600×800.

Open the sheet with Enter on the burger → Tab moves into the page
*behind* the sheet; Tabs 6–14 land on elements at document
y = 1146–2081 px while the viewport is 800 px and scroll-locked at 0 —
focus is completely invisible and the page won't scroll to it. The
menu is only enterable *backwards* (two Shift+Tabs from the burger).
The sheet's height-cap/scroll-lock is the documented gotcha; the
focus order is not covered there — new angle. WCAG 2.4.3.

**Suggested direction:** on open, move focus to the first item in
`#site-nav-links` (Escape already returns to the burger); or reorder
the DOM so the burger precedes the sheet. Closing on focusout would
also stop the invisible-focus tail.

#### 7. Calculator results update silently — zero live regions under `/tools/`, and the PID tuner readouts are silent too — **medium**

**Location:** all 14 tools (the property-sheet Output column);
`/simulators/pid-tuner.html` readouts (#pid-over/#pid-settle/#pid-err).
**Lens:** a11y. **Verified:** grep — `aria-live`/`role=status` exist
only on 4 simulators + the quiz engine; live check on signal-scaling
confirms the output span has no live ancestor (its `live` class is
visual chrome only). Issue #21's a11y bundle never touched live
regions.

**Suggested direction:** `role="status"` on the Output column's
readout container in the property-sheet pattern; a throttled polite
region for the PID readouts (announce on settle).

#### 8. Tab pattern on 12 tool pages exposes no state or relationship to assistive tech — **medium**

**Location:** `.tab-btn` via `switchTab` in `scripts/ui.js` — zero
aria handling; active tab is class-only. All 12 tab-carrying tools.
**Lens:** a11y. **Verified:** live on signal-scaling +
modbus-register-viewer; distinct from codebase-issues #17 (wiring
consolidation) and ux-audit #9 (touch height).

A screen reader announces three identical-sounding plain buttons with
no indication one is selected or that activating swaps the panel.
(Note: the minimal `aria-pressed` fix is semantically imperfect for a
tab idiom — proper `role=tablist/tab/tabpanel` + `aria-selected` is
the clean version.)

**Suggested direction:** toggle `aria-selected` with tablist roles in
`switchTab`'s existing classList pass.

#### 9. Modbus register viewer bit grid is mouse-only — **medium**

**Location:** `/tools/modbus-register-viewer.html` — 16 `div.bit`
cells toggle register bits on click but have no tabindex, role, or
accessible name; tabbing skips them entirely. **Lens:** a11y.
**Verified:** live (clicking last cell flips #mod-dec 0→1); distinct
from content-audit #23 (tap-target *size*, addressed) — keyboard/AT
access was never filed.

A keyboard-only user wanting to flip one bit must do the binary
arithmetic by hand and retype the decimal.

**Suggested direction:** make each bit a `<button>` (or
`tabindex=0` + `role=switch`) named like "Bit 11, value 1" with
`aria-pressed`; the click handler already does the work.

#### 10. Psychrometric chart state-point selector is a `role=tablist` with no tabs — active point conveyed visually only — **medium**

**Location:** `/tools/psychrometric-chart.html` — `.psy-pills` carries
`role="tablist"` but children are plain buttons with no `role=tab` /
`aria-selected` / `aria-controls`; the only tablist on the site, with
zero `role=tab` anywhere; disabled-stage dimming is opacity-only.
**Lens:** a11y. **Verified:** live + grep.

The half-applied pattern actively misleads: a screen reader announces
"tab list" then seven stateless buttons, and there's no way to hear
which state point is being edited.

**Suggested direction:** complete the pattern (roles + roving
tabindex) or drop `role=tablist` and use `aria-pressed`/`aria-current`
plus `aria-disabled` for off stages.

### Performance & delivery

#### 31. flow-engine gutter flows saturate the main thread at idle on every page — including animating 552 invisible particles when the gutter is `display:none` on phones — **high**

**Location:** `scripts/flow-engine.js` rAF loop (~216–253) +
`schematic-bg.njk` — all 66 pages. **Lens:** performance.
**Verified:** fully re-reproduced; arithmetic and frame counts match.

The rAF loop ticks every `data-flow` particle pool every frame
unconditionally — the IntersectionObserver gates **pulses only**. The
gutter motifs alone create 552 particles on a chrome-only page
(privacy.html). Measured over 10 s idle windows: at 1600 px the main
thread is ~100 % busy doing nothing (TaskDuration ≈ 10,000 ms/10,000 ms;
27–44 fps idle); with reduced motion the same pages cost
123–174 ms/10 s — the engine is **>98 % of all idle cost**. At a 390 px
phone viewport the gutter is `display:none` but the pools are still
built and ticked: 4.5 s of script per 10 s at 1× CPU, and at 4× CPU
throttle (mid-range phone) the thread is fully consumed moving circles
that never paint (layout = 0 ms). 552 particles × 60 fps ≈ 33 k
`getPointAtLength` + 66 k `setAttribute` calls/sec. This directly
contradicts deferred #70's recorded rationale ("the
IntersectionObserver-gated per-frame work … keeps the CPU cost
negligible") — that gating never applied to flows, so this is the new
angle #70's carve-out anticipates, not a re-report.

**Suggested direction:** three independent fixes, cheapest first:
(1) don't build/tick pools inside a hidden `.schematic-bg`
(`matchMedia('(min-width: 1240px)')` check + re-check on change) —
zeroes the phone cost; (2) extend the existing IntersectionObserver to
flow pools (~80 % desktop reduction at typical scroll positions);
(3) tick gutter flows at 30 fps. Update #70's CPU claim either way.
